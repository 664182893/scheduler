# Scheduler 学习路线图（16 张任务卡）

> 来源：《8 周学习 + 健身执行计划（源码攻坚版）》T 系列任务卡。
> 线定位：调度的地基——单个 Pod 怎么选节点。
> 用途：换机器后的完整考纲。每张卡都带问题 / 动作 / 交付 / 验收 / 卡点，验收时直接按「验收」一行考。

## 阅读顺序（原文）

`interface.go` 是字典，`schedule_one.go` 是小说。顺序是：

1. 先看它跑（T0-1）
2. 让它失败一次（T0-2）
3. 追一次成功路径（T1-1）
4. 遇到不认识的名字，才回去查 `interface.go`

## Tier 0 · scheduler · 热身

> 不改一行代码，先让调度器把话说出来

### T0-1 让调度器说话

**时长**：40 min

- **问题**：一个 Pod 从入队到绑定成功，调度器到底打了哪些日志？那 11 个扩展点分别对应哪几行？
- **动作**：kind 起单节点集群 → 把 scheduler 日志级别调到 5 → 创建 1 个 nginx Pod，全程盯着日志。kind 配置里加这一段即可：`kubeadmConfigPatches` 里给 `scheduler.extraArgs` 设 `v: "5"`
- **交付**：把日志按阶段切成 6 段，每段旁边标注对应的扩展点名
- **验收**：能指着某一行说「这里是 Filter 跑完了」「从这里进 binding cycle」
- **卡点**：kind 里调度器是静态 Pod，改参数要改节点上的 manifest。嫌麻烦就先用 `kubectl get events -w` 拿 80% 的信息，日志级别以后再补

### T0-2 亲手制造一次 FailedScheduling

**时长**：30 min

- **问题**：`0/9 nodes are available: 3 Insufficient cpu, 5 node(s) didn't match...` 这句话是谁拼出来的？
- **动作**：造两个必然失败的 Pod：一个 request 999 CPU，一个 nodeSelector 打一个不存在的 label。看 events，再对比日志
- **交付**：events 原文 + 源码里拼这句话的函数（直接全局搜 `nodes are available` 这个字符串，比猜文件名快十倍）
- **验收**：能解释为什么 events 只给你一句话，而日志里有更多细节
- **卡点**：别从 pkg/scheduler 根目录一个个文件翻，先搜字符串定位，再往上追调用方

## Tier 1 · scheduler · 解剖

> 带着问题读，不是通读

### T1-1 追一个 Pod 的一生

**时长**：90 min · 拆 3 次

- **问题**：从 informer 收到 Pod，到 bind 结果写回 apiserver，中间到底调了哪些函数？
- **动作**：从 `scheduleOne` 开始，一个函数一个函数往下跟。每个函数记三样：**文件:行号**、一句话职责、它返回值被谁用了
- **交付**：一张调用链图，至少 15 个节点，每节点带位置
- **验收**：不看图，能口述完整链路。你会发现调度器其实只有一条主干，比你想象的简单得多
- **卡点**：不要一上来读全部。先只追主干（schedulePod → findNodesThatFitPod → prioritizeNodes → assume → bind），旁支全部跳过

### T1-2 找到那个 goroutine 的边界

**时长**：45 min

- **问题**：KEP 说 binding cycle 可以并发，代码里这个并发点到底在哪一行？
- **动作**：在 `scheduleOne` 里搜 `go func`，再搜 `bindingCycle`
- **交付**：画出「主线程走到哪一步、goroutine 从哪接手」的分叉图
- **验收**：能解释为什么 permit 之前的扩展点必须同步执行——这一个问题搞懂，KEP 的并发那一节就通了
- **卡点**：搜 `bindingCycle` 比搜 `go func` 稳，后者会命中几十处

### T1-3 多个插件怎么合并成一个分数

**时长**：60 min

- **问题**：3 个 Score 插件打分尺度完全不一样（有 0–10 的，有 0–100 的），最后怎么比大小？
- **动作**：读 `RunScorePlugins`，找到 NormalizeScore 和权重相乘的位置
- **交付**：手算一个「3 插件 × 2 节点」的例子，算出最终排名
- **验收**：能回答：如果某个插件不实现 NormalizeScore 会发生什么？（答案：尺度大的插件独占话语权——这正是 extender 时代的老坑）
- **卡点**：这一张和上一轮聊的 extender 局限性是同一个问题，对照着看会很快

## Tier 2 · scheduler · 改造

> 第一次让调度器按你的意志动 —— 这是全计划的动力拐点

### T2-0 先把 kube-scheduler 编译出来

**时长**：60 min

- **问题**：改一行代码，怎么让它变成能跑的东西？这一步不做，后面 T2-1 一定会卡住。
- **动作**：`git clone --depth 1 --branch v1.31.0 <kubernetes 仓>` → `cd kubernetes && go build ./cmd/kube-scheduler`（版本挑一个和你集群接近的）
- **交付**：一个能执行的 `kube-scheduler` 二进制
- **验收**：`./kube-scheduler --version` 打印出你编译的版本号
- **卡点**：仓库 3GB+，**必须用 `--depth 1`**。Go 版本要和 `go.mod` 第一行对齐，不对齐会报一堆完全看不懂的错——这是新手最常见的劝退点，遇到就先去对齐版本，别怀疑代码

### T2-1 第一个插件：只打一行日志

**时长**：45 min

- **问题**：怎么让 kube-scheduler 加载我自己写的代码？
- **动作**：走**快路径**：fork k8s → 在 `pkg/scheduler/framework/plugins/` 下新建目录 → 注册进 `registry.go` → `go build ./cmd/kube-scheduler`。插件里只在 Score 打一句日志
- **交付**：一个能编译的二进制 + 一份能加载它的配置
- **验收**：Pod 调度时，`kubectl logs` 里出现你插件的日志
- **卡点**：**别一上来用 out-of-tree 方式**（独立 module + WithPlugin）。k8s.io/kubernetes 的依赖管理会让新手卡掉一整个下午，这是最典型的动力杀手。学习阶段走 fork 直接注册，能跑通再考虑解耦

### T2-2 让分数真正决定 Pod 去哪

**时长**：60 min

- **问题**：我的分数怎么影响最终选择？权重到底是干嘛的？
- **动作**：读节点 label `gpu-model`：A100 给 100 分，H100 给 10 分，插件 weight 设大
- **交付**：两个 label 不同的节点，调度后 Pod 落在 A100 上
- **验收**：把 weight 从大调小，调度结果跟着变——说明你真的控制住了决策，而不是碰巧
- **卡点**：Score 返回值必须在 [0, 100] 内，越界整个调度周期直接失败，而且报错很不直观

### T2-3 从软偏好升级成硬约束

**时长**：60 min

- **问题**：什么时候该用 Filter 而不是 Score？两者边界在哪？
- **动作**：把 T2-2 改写成 Filter：只有 gpu-model 匹配的节点才放行
- **交付**：不匹配时 Pod 一直 Pending，且 event 里出现你插件返回的原因
- **验收**：你的插件名出现在 `FailedScheduling` 的 message 里——这一刻你就掌握了调度排障最关键的可观测点
- **卡点**：Filter 返回的 Status 里那个 reason 字符串，会被拼进 event。写得清楚一点，以后自己救自己

### T2-4 给插件写单测

**时长**：60 min

- **问题**：没有集群的时候，怎么验证插件逻辑是对的？
- **动作**：table-driven test，手搓 `v1.Node` 和 `framework.NewNodeInfo()`
- **交付**：`go test` 全绿 + 至少 3 个 case（匹配 / 不匹配 / label 缺失）
- **验收**：故意改坏一行代码，测试必须变红。没红说明你的测试是假的
- **卡点**：用 `framework.NewNodeInfo()` 构造，别想着 mock 整个 Framework 接口

## Tier 3 · scheduler · 硬核

> 面试能讲 20 分钟的部分，也是唯一必须读懂 KEP 才能做的

### T3-1 Permit：手写一个简化版 gang（只做最小版）

**时长**：90 min

- **问题**：怎么让一个 4 副本的 Job 要么全部调度成功，要么一个都不调度？
- **动作**：Permit 里维护计数器：不足 4 个返回 Wait，第 4 个到达时把前面 3 个一并 Allow。只跑通主干，不做边界处理
- **交付**：一个 4 副本 Job + 完整的调度日志
- **验收**：把集群资源压到只够 3 个 Pod，观察 3 个全部卡在 Wait，超时后一起回队列
- **卡点**：**这一张的目的不是做出可用产品，是给自己造一个对照样本。**W5 的 V2-1 会读生产级 gang 实现，到时候你会发现你漏掉的边界正是它 80% 的代码。做不出来别硬扛，先做 T3-3 再回来

### T3-2 Unreserve：验证回滚真的幂等

**时长**：90 min

- **问题**：绑定失败了，我在 Reserve 里预留的东西怎么回收？为什么 KEP 强调「幂等且不可失败」？
- **动作**：Reserve 里往内部 map 写状态，Unreserve 里清；再故意让 Bind 返回 error
- **交付**：日志证明 Unreserve 被调用了，且重复调用不 panic
- **验收**：能用自己的话讲清楚：为什么这里一旦 panic，整个调度器就停了
- **卡点**：用配置一个必然失败的 Bind 插件来触发，别去改 apiserver

### T3-3 CycleState：跨扩展点传状态

**时长**：60 min

- **问题**：PreFilter 里算出来的数据，Score 阶段怎么拿到？
- **动作**：PreFilter 里 `state.Write`，Score 里 `state.Read`。同时写一个「插件自己存 map」的版本做对比
- **交付**：两种实现的代码 + 一段结论
- **验收**：能说出后者在并发调度下会出什么问题（提示：两个 Pod 同时调度，数据串台）
- **卡点**：CycleState 在调度上下文结束后立即失效，别把里面的指针存下来长期持有

## Tier 4 · 收口 · 数据

> 把「我写过」变成「快了多少」

### T4-1 kwok 造 2000 节点跑对比压测

**时长**：180 min · 周末

- **问题**：我的插件在 2000 节点规模下有多慢？慢在哪个扩展点？
- **动作**：kwok 造 2000 个模拟节点，同一批 Pod 分别跑 default-scheduler 和你的插件
- **交付**：三组数字：调度吞吐（pods/s）、P99 调度延迟、Score 阶段耗时
- **验收**：有对比表格，且能指出瓶颈落在哪个扩展点
- **卡点**：kwok 的节点是模拟的，指标只能比**相对差异**，绝对值和真机没有可比性——写简历时别写成「支持 2000 节点」

### T4-2 一页纸压测报告

**时长**：90 min

- **问题**：怎么让一堆数字变成别人愿意读完的东西？
- **动作**：五个部分：方法论 / 环境 / 三组数据 / 结论 / 局限
- **交付**：一页 markdown 或 PDF
- **验收**：一个不懂调度的人看完，能说出「你的插件比默认慢多少、值不值得上」
- **卡点**：必须写「局限」。没有局限的报告，面试官一眼就看出是编的

## Tier 5 · 收口 · 输出

> 把 8 周变成一个可验证的外部凭证

### T5-1 一篇能发出去的文章

**时长**：180 min · 周末

- **问题**：怎么让别人相信这些是你真做过、而不是看会的？
- **动作**：写《我给 K8s 写了个 GPU 调度插件，踩了 N 个坑》。**重点写坑，不写成功**——成功谁都能编，踩坑编不出来
- **交付**：发出去。掘金 / 知乎 / 公司内网 / 技术群，任何一个都算
- **验收**：有非同事的人评论或提问
- **卡点**：别等「全做完再写」。T2-3 做完就可以起笔，后面边做边补
