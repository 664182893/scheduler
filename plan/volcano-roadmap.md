## Tier V · Volcano（生产在跑）

> V0 上手排障 → V1 架构 → V2 核心插件 → V3 自己写一个

### V0-1 先确认它到底是不是 kube-scheduler 的 fork

**时长**：30 min

- **问题**：Volcano 和 kube-scheduler 是什么关系？同名不同源，还是真的 fork？
- **动作**：clone volcano → `go list -deps ./pkg/scheduler | grep k8s.io/kubernetes` → 再看 `pkg/scheduler/framework` 的目录结构
- **交付**：一条命令的输出 + 一句结论
- **验收**：能说清「两套 framework 同名不同源」，并解释为什么不直接复用
- **卡点**：这个认知决定了你后面读代码的姿势：**不能拿 kube-scheduler 的经验硬套**。两边都有 Session / Plugin / Tier，长得像但语义不同，混着套会越读越乱

### V0-2 在集群里看一次真实的 gang 调度

**时长**：45 min

- **问题**：一个 vcjob 提交后，PodGroup 从 Pending 到 Running，中间经历了什么？
- **动作**：提交一个 4 副本 vcjob，同时 `watch kubectl get pg,vcjob,pod`，再抓 volcano-scheduler 日志
- **交付**：PodGroup 各阶段的时间线 + 对应时段的调度器日志
- **验收**：故意申请超过集群余量的资源 → PodGroup 卡在 Pending，**一个 Pod 都不启动**
- **卡点**：gang 的真实体感**不是「部分成功然后慢慢补」，是「完全不启动」**。回想你 T3-1 写的那个版本，行为一致吗？

### V0-3 排一次真实的调度失败（最重要的一张）

**时长**：60 min

- **问题**：生产里 vcjob 一直 Pending，怎么快速定位卡在哪个环节？
- **动作**：从 PodGroup 的 condition / event 反查，对应到 `enqueue` / `allocate` 哪个 action；再对照 Queue 的配额
- **交付**：**一张「症状 → 可能原因 → 看哪个字段/日志」的排障表**
- **验收**：能一眼区分四种情况：队列配额不足 / 集群资源不足 / gang 凑不齐 / 亲和性不匹配
- **卡点**：**这张表是整个 8 周里唯一能立刻改善你工作质量的东西。**打印出来贴在工位旁边，以后值班不用现查

### V1-1 三个抽象为什么必须拆开

**时长**：60 min

- **问题**：Job / PodGroup / Queue 为什么要拆成三个对象？合成一个不行吗？
- **动作**：读 controller 部分，同时 `kubectl get vcjob,pg,queue -o yaml` 对着看字段
- **交付**：三者关系图 + 一张「哪个字段属于哪一层」的对照
- **验收**：能解释「作业信息放 Job、调度信息放 PodGroup」这个拆分带来的好处
- **卡点**：看一个细节就懂了：**`MinMember` 在 PodGroup 里，不在 Job 里**。这个位置本身就是答案——它是调度参数，不是作业参数

### V1-2 Session 为什么必须周期驱动

**时长**：60 min

- **问题**：为什么 Volcano 要每 1 秒全局扫一遍，而不能像 kube-scheduler 那样来一个 Pod 调一次？
- **动作**：读 `Run` / `runOnce` / `OpenSession` / `CloseSession`，画出快照的生命周期
- **交付**：一段对比说明 + 一张快照生命周期图
- **验收**：能回答：**如果改成事件驱动，gang 判定会坏在哪？**（单 Pod 触发时看不到同组其他 Pod 的状态）
- **卡点**：同一个问题在 kube-scheduler 里是靠 **Permit** 解决的（T3-1 你亲手试过）。两条路你都有体感了，这时候再问「哪条更好」，就是你自己的判断了

### V2-1 gang plugin 的判定逻辑（对照你写的幼稚版）

**时长**：90 min

- **问题**：gang 插件凭什么决定一个 Job 能不能开始分配？`MinMember` 和 `MinResources` 冲突时谁优先？
- **动作**：读 `pkg/scheduler/plugins/gang`，找 `jobReady` / `jobPipelined` / `jobValid`
- **交付**：一张判定流程图，每个分支标注输入是什么
- **验收**：能说清「成员齐了但资源不够」和「资源够了但成员没齐」分别怎么处理
- **卡点**：**拿 T3-1 你写的版本对照着看。**你当时一定漏掉了某些边界，而那些边界正是生产版 80% 的代码量——这个落差就是你今天最大的收获

### V2-2 Queue 的配额与回收

**时长**：60 min

- **问题**：为什么不直接用 ResourceQuota，而要搞一套 Queue + proportion + reclaim？
- **动作**：读 proportion / reclaim 插件；观察一次某队列配额占满时的实际行为
- **交付**：一张「配额怎么算、什么时候触发回收、回收谁」的说明
- **验收**：能解释这个最常见的问题：**集群明明有空闲卡，我的任务为什么还是进不去**（配额被别的队列占了，且没触发回收）
- **卡点**：这是生产里最容易被业务方抱怨、也最容易被解释错的问题。搞清楚回收条件，你就能给出确定答复而不是「再看看」

### V3-1 给 Volcano 写一个 plugin（唯一的产出型任务）

**时长**：120 min · 周末

- **问题**：怎么让 Volcano 按你的规则调度？比如 GPU 型号亲和、NUMA 对齐、拓扑就近。
- **动作**：仿照 `nodeorder` 或 `predicates` 写一个插件，注册对应的 `*Fn`，编译进 volcano-scheduler 镜像
- **交付**：能编译的镜像 + 生效证明（调度结果因你的规则而改变）
- **验收**：日志里能看到你的插件参与决策；改个参数，Pod 落点跟着变
- **卡点**：比 kube-scheduler 插件简单得多（**没有 CycleState、没有 Unreserve、没有多阶段生命周期**），但官方文档几乎没有，主要靠读现成插件抄结构。**这一张是整个 8 周唯一直接产出于生产环境的东西**
