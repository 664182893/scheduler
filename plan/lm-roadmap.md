## Tier M · 大模型框架

> M0 体感 → M1 推理 → M2 训练 → M3 会师

### M0-1 让 vLLM 吐出第一个 token

**时长**：45 min

- **问题**：一个模型从加载进显存，到吐出第一个字，中间到底发生了什么？
- **动作**：vLLM 起一个 OpenAI 兼容服务 → curl 打一次 → 记录首字延迟（TTFT）和总耗时
- **交付**：一条可复用的 curl 命令 + 一次完整响应 + 显存占用截图（`nvidia-smi`）
- **验收**：能解释 **prefill**（一次性算完 prompt）和 **decode**（逐 token 生成）是两件完全不同的事，且瓶颈不一样
- **卡点**：模型下载容易卡半天。先用 0.5B–7B 的小模型跑通，别一上来 70B。想拿好数据再换大模型

### M0-2 打开张量并行

**时长**：60 min

- **问题**：模型比单卡显存大时，vLLM 是怎么把它切开的？
- **动作**：`--tensor-parallel-size 2`，对比 TP=1 与 TP=2 的吞吐、TTFT、单卡显存
- **交付**：一张 TP=1 vs TP=2 对比表
- **验收**：能解释**为什么 TP 不是越大越好**（每层都要 all-reduce，通信会把收益吃掉）
- **卡点**：需要 ≥2 卡。只有 1 卡就改成扫 batch size 做对比，结论一样能推出来

### M1-1 PagedAttention 到底解决了什么

**时长**：60 min

- **问题**：为什么 vLLM 的吞吐能比朴素的 HuggingFace generate 高好几倍？
- **动作**：只读 vLLM 的 KV cache / block manager 这两个部分 + 论文里那张对比图
- **交付**：一张图：从「按最大长度预分配连续显存」到「按页分配」的变化
- **验收**：能解释**显存碎片率如何直接决定「同时能跑几个请求」**
- **卡点**：不要试图读完 vLLM。它的代码量超出运维该读的范围，只看显存管理这一条线就够

### M1-2 找到吞吐的拐点

**时长**：45 min

- **问题**：并发继续加，为什么吞吐会突然不涨反跌、延迟直接爆炸？
- **动作**：用 vLLM 自带 benchmark 脚本，扫 1 / 4 / 8 / 16 / 32 并发
- **交付**：一张「并发 - 吞吐 - 延迟」三线图
- **验收**：能指出拐点在哪，并解释它由什么决定（KV cache 用尽 → 开始抢占 preemption → 重算）
- **卡点**：这个拐点就是你以后回答「为什么加了卡还是慢」的底气，比任何概念都有用

### M2-1 3D 并行到底在切什么

**时长**：90 min

- **问题**：TP / PP / DP 分别切的是什么？为什么大模型必须三个一起用？
- **动作**：画一张 8 卡 = TP2 × PP2 × DP2 的切分图，标出每张卡各自存了哪部分参数、哪部分激活
- **交付**：切分图 + 一张「多大模型该用哪种组合」的经验表
- **验收**：能解释**为什么 PP 会产生 pipeline bubble，而 TP 不会**
- **卡点**：先看 Megatron-LM 论文的图 2，别看代码。代码会把你劝退，图看懂就够了

### M2-2 跑一次最小分布式训练

**时长**：120 min · 周末

- **问题**：分布式训练启动时，各个 rank 是怎么找到彼此、怎么开始通信的？
- **动作**：用 `torchrun` 或 Megatron 起一个 2 卡的小模型训练（几层 transformer 就行）
- **交付**：启动日志 + 一张 rank 拓扑图
- **验收**：能指出日志里**哪一行是 NCCL 建链、哪一行是第一次 all-reduce**
- **卡点**：环境是最大障碍。直接用 NGC 的 PyTorch 镜像，别自己装 CUDA/NCCL。没多卡就用 gloo + CPU 跑通流程，机制完全一样

### M2-3 checkpoint 的真实代价

**时长**：60 min

- **问题**：训练为什么要存 ckpt、存一次到底要多久、恢复又有多慢？
- **动作**：观察一次 ckpt 保存，记录文件大小、保存耗时、恢复耗时
- **交付**：三个数字 + 一句结论
- **验收**：能解释为什么大模型训练的「有效算力」会被 ckpt 吃掉一块
- **卡点**：这张直接连到调度：**ckpt 期间所有 rank 空转，但卡全占着**。这就是集群利用率上不去的隐形杀手之一

### M3-1 训练任务对调度的真实要求

**时长**：90 min

- **问题**：一个 8 节点 × 8 卡的训练任务，调度器必须保证什么？
- **动作**：列约束清单：同时启动、同 IB fabric / 同交换机、NVLink 拓扑、不能部分调度、失败要整体回收
- **交付**：一张「训练需求 → 对应 scheduler 扩展点」的映射表
- **验收**：能说清**为什么默认调度器做不好这件事**（没有 gang、没有拓扑感知、失败了不会整组回滚）
- **卡点**：这张表就是 T3-1 的理论依据。先做 T3-1 再回来填表会更快，顺序可以换

### M3-2 用 Volcano 调度一个真实训练任务（会师点）

**时长**：150 min · 周末

- **问题**：一个多节点 × 多卡的训练任务，从提交到全部 Running，每一步撞到哪条规则？
- **动作**：用 vcjob 起一个 2 节点训练任务（或复现一次生产的真实任务），全程记录 PodGroup phase、Queue 配额、调度器决策日志；顺手把 M3-1 的「训练需求 → 规则」映射表填掉
- **交付**：一份「任务启动全过程」时间线，每个阶段标注它被哪条规则检查过
- **验收**：把 Queue 配额或集群余量压到只够一半 → 任务**整体 Pending**，且你能说清是哪个 action 拦下来的
- **卡点**：**这是三条线的会师点。**做完这张，「为什么我的训练任务起不来」的每一个分支你都能当场答出来——这比任何证书都值钱，因为它是你每天都在被问的问题
